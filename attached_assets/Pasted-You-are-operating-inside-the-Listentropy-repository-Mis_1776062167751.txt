E. Build centralized storage carefully
The system should support storing consented user data centrally, but in a disciplined way.
Do NOT treat this as “dump everything into one database”.
You must design and implement:
- a user-scoped private/raw data layer
- a derived user-private analytics layer
- a privacy-preserving aggregate analytics layer for cross-user dashboards
- explicit separation of concerns between these layers

Design requirements:
- raw/private user listening data remains access-controlled and user-scoped
- aggregate analytics are derived from private data through a defined pipeline
- aggregate tables should not expose user-identifiable records
- provenance should always show whether a metric came from:
  - Spotify API
  - uploaded export
  - merged data
  - aggregate cross-user analytics

G. Aggregate analytics / home dashboard
Design and implement a home dashboard backed by cross-user aggregate analytics, but do so safely.

Requirements:
- define exactly which aggregate metrics are useful and defensible
- build aggregation jobs / derivation flows
- add guardrails such as:
  - minimum cohort thresholds
  - suppression of low-count slices
  - no direct exposure of row-level user listening data
  - no unique-user fingerprinting surfaces
- ensure the dashboard only uses appropriately derived aggregate tables
- document tradeoffs and residual privacy risks honestly

Examples of acceptable aggregate patterns:
- top artists/tracks across sufficiently large cohorts
- genre/time/behavior aggregates above minimum thresholds
- comparative percentile-style metrics only if implemented safely

Examples of risky patterns to avoid unless carefully protected:
- narrow cohort slices
- exact rare listening histories
- user-level raw event exposure
- dashboards where a single user can infer another user’s private behavior
